| 产品一句话定义 | 让普通人提出真实需求、用付费承诺筛选优先级，由开发者提案竞标并交付，验收达标后放款的一个社区驱动开发平台。 |

---

## 1. 背景与问题

### 1.1 现状

- 用户有大量真实但分散的需求，缺少一个能被看见、能被验证、能被兑现的机制。
- 现有产品中，投票类（如各类需求墙）只解决"表达"，众筹类（如 Kickstarter）只解决"筹资"，外包/悬赏类只解决"开发"，三者彼此割裂。
- 结果：大量"高票需求"无人实现；大量开发者做了没人要的东西；出资人承担了烂尾风险。

### 1.2 核心洞察（本产品的立论基础）

参考 LEGO Ideas 的运行机制（10,000 票仅进入评审、约 1/3 过票项目被量产、官方保留最终设计权并大幅调整），得出三条设计原则：

1. **票 ≠ 钱**：投票是零成本热度，付费承诺才是真信号。投票用于发现和排序，不能作为启动开发的依据。
2. **需求 ≠ 方案**：群众擅长指出痛点，不擅长给出可执行的规格。需要一个"专业转化层"把需求翻译成可做方案。
3. **验收 ≠ 一句话满意度**：投票可被刷、开发者会拉票、烂尾难追责。必须用资金托管 + 里程碑放款 + 付费用户真实反馈来约束。

> 本产品的真正壁垒不是"把投票和钱连起来"，而是"设计一套把零成本热度转化为真实付费承诺的机制"。

## 2. 产品定位与目标

### 2.1 定位

一个聚焦垂直领域的**需求发现 + 付费承诺 + 方案竞标 + 托管交付**平台。不做全品类、不做全人群，先在一个窄口跑通闭环。

### 2.2 产品目标

| 阶段 | 目标 |
| --- | --- |
| 短期（MVP） | 验证"付费承诺"能否替代"投票热度"成为有效需求信号 |
| 中期 | 跑通 3～5 个从需求到交付的完整案例，形成可复制流程 |
| 长期 | 成为某垂直领域内"有什么需求值得做"的默认发现与验证平台 |

### 2.3 成功指标（North Star）

- **核心指标：付费承诺转化率** = 产生有效付费承诺的需求数 / 获得 100+ 票的需求数
- 辅助指标：需求数、提案数/需求、承诺金额达标率、项目按时交付率、交付后退款率、复购率

### 2.4 非目标（明确不做）

- 不做社交/社区泛内容
- 不做股权投资、返利、保本承诺类募资（见第 9 节合规）
- 不做全品类覆盖

## 3. 用户角色

| 角色 | 描述 | 核心诉求 |
| --- | --- | --- |
| 需求发起者 Requester | 提出痛点的普通用户 | 需求被看见、被解决 |
| 支持者 Backer | 投票并做出付费承诺的用户 | 用钱投票，买到真正想要的东西 |
| 开发者 Builder | 提交方案并承接开发 | 找到有真实付费意愿的项目 |
| 运营方 Operator | 平台方 | 维护规则、控风险、撮合交易 |

---

## 4. 核心流程（五步闭环）

```
提需求 → 投票排序 → 付费承诺（达标触发）→ 开发者提案竞标 → 开发 / 里程碑验收 → 放款 + 评价
```

### 4.1 需求生命周期状态机

`草稿 → 征集投票 → 进入付费承诺 → 承诺达标(解锁开发) → 方案竞标 → 开发中 → 里程碑验收 → 已完成 / 已流拍 / 已退款`

关键规则：
- 只有"付费承诺金额"达到目标，需求才进入开发阶段（票数仅用于排序和曝光）。
- 未达标的需求，承诺全额原路退还，不产生任何扣款。
- 每个阶段有明确时限，超时自动流转或退款。

### 4.2 三条断点的对应机制

| 断点 | 机制设计 |
| --- | --- |
| 票 ≠ 钱 | 引入"付费承诺"（预购订金，可退）；承诺金额达标才触发开发；票只决定曝光顺序 |
| 需求 ≠ 方案 | 开发者的提案必须包含：需求理解、可执行规格、报价、工期、里程碑；社区用钱+投票选方案 |
| 验收博弈 | 资金第三方托管、按里程碑放款；验收依据付费用户的确认收货 + 退款率，而非单纯满意度投票；反刷票机制 |

## 5. 功能需求

优先级：P0 = MVP 必须；P1 = 第二阶段；P2 = 后续。

### 5.1 需求模块

- **P0** 需求发布：标题、痛点描述、目标人群、期望形态、图片/附件
- **P0** 需求列表与详情：按付费承诺金额、票数、时间排序
- **P0** 需求状态展示与生命周期流转
- **P1** 需求模板与发布引导（帮助群众把痛点写清楚）
- **P2** 需求合并 / 相似需求去重

### 5.2 投票与排序

- **P0** 登录用户一人一票，可对需求投"支持"
- **P0** 榜单：热度榜（票数）/ 承诺榜（金额）
- **P1** 反刷票：设备指纹、异常投票检测、新账号权重限制
- **P2** 投票理由与评论区

### 5.3 付费承诺（核心）

- **P0** 用户对需求做"付费承诺"（预购订金），写明金额
- **P0** 承诺目标进度条（已承诺 / 目标金额、剩余时间）
- **P0** 资金托管：承诺款进入第三方托管账户，未达标全额原路退回
- **P0** 达标判定：截止时间到期或提前达标 → 解锁开发阶段
- **P1** 承诺档位（如 9.9 / 49 / 99 元不同权益）
- **P1** 退出承诺机制（截止前可撤，截止后锁定）

### 5.4 开发者提案竞标

- **P0** 开发者针对已进入开发阶段的需求提交提案
- **P0** 提案必填项：需求理解、执行规格、报价、工期、里程碑划分、过往案例
- **P0** 支持者选择提案（用付费承诺对应的"选票"），选定中标方案
- **P1** 开发者实名 / 资质认证与评分
- **P1** 提案问答与澄清区

### 5.5 开发与里程碑交付

- **P0** 里程碑拆分与节点提交（每个节点含交付物说明）
- **P0** 支持者对每个里程碑确认验收 / 提出异议
- **P0** 资金按里程碑比例释放给开发者
- **P1** 交付物托管与预览（代码仓库 / 文件 / 演示链接）
- **P2** 争议仲裁流程

### 5.6 验收与结算

- **P0** 最终验收：付费用户确认 + 退款窗口期
- **P0** 结算：达标放款，未达标退款
- **P1** 交付后评价与评分（开发者、项目双向）
- **P1** 退款率统计并进入开发者信誉

### 5.7 用户与信任

- **P0** 注册登录（手机号 / 邮箱）
- **P0** 实名认证（涉及资金，必须）
- **P0** 用户信誉分基础版（履约次数、退款率）
- **P1** 开发者认证与作品集

### 5.8 管理后台

- **P0** 需求 / 提案 / 项目审核
- **P0** 资金流水与托管状态查看
- **P0** 举报与处理
- **P1** 数据看板

## 6. 关键机制详细说明

### 6.1 付费承诺如何工作

1. 支持者在承诺期内对某需求支付订金 → 进入托管。
2. 展示实时进度（金额、人数、剩余时间）。
3. 到期未达标 → 全额原路退回，需求转入"未达成"归档。
4. 达标 → 锁定资金，需求进入提案竞标；资金最终按里程碑释放。
5. 项目烂尾 / 严重不符 → 按规则退还剩余未释放款项。

### 6.2 方案竞标如何工作

- 一个需求可收到多个提案，公开透明。
- 支持者用其承诺金额对应的权重选择方案（避免马甲刷票）。
- 中标方案签约后进入开发；未中标提案不产生费用。

### 6.3 反刷票与反操纵

- 实名 + 一人一票；设备 / 支付账户去重
- 新账号冷却期，异常增长检测
- 投票与承诺分离：只有付费承诺才计入解锁

## 7. MVP 范围（建议）

### 7.1 垂直领域建议

优先选择**数字化程度高、交付可验证、受众聚焦**的领域，例如：
- 办公 / 效率小工具
- 特定人群的实用 App 功能

理由：开发成本可控、交付物易确认、验收标准清晰，便于跑通闭环。

### 7.2 MVP 包含

- 需求发布 + 投票 + 排序
- 付费承诺 + 托管 + 达标判定（可先用模拟/线下托管跑通逻辑）
- 开发者提案 + 中标选择
- 里程碑 + 验收 + 放款/退款
- 实名认证 + 基础后台

### 7.3 MVP 不包含

- 全品类、社区内容、复杂社交
- 股权投资 / 收益承诺
- 自动仲裁、AI 需求拆解（后续）

## 9. 合规与风险（重点）

> 公开向陌生人募资并承诺回报，在国内极易触碰非法集资 / 非法吸收公众存款红线。本产品必须在设计上规避。

必须遵守：
1. 定位为**商品/服务的预购与定制**，而非投资、募股、返利。
2. **绝不承诺固定收益、股权、保本、回报倍数**。
3. 资金进入**持牌第三方支付/银行托管账户**，平台不池资金、不自建资金池。
4. 明确披露：项目风险、交付不确定性、退款规则。
5. 实名认证 + 单笔/单人额度限制。
6. 上线前请专业律师出具合规意见，并根据属地监管要求调整。

其他风险：刷票、开发者烂尾、交付不符、需求涉侵权/违规内容 —— 均需对应风控与审核机制。

## 10. 冷启动策略

三边市场（需求方 / 出资方 / 开发者）不能同时点火，建议：

1. **先聚供给端**：邀请一批靠谱开发者或一个小而美团队，确保"有人能交付"。
2. **再聚需求端**：在一个窄领域内收集 20～30 个真实痛点，筛出 3～5 个高共鸣需求。
3. **用种子用户做付费承诺**：小范围验证"愿不愿意掏钱"，而不是先追票数。
4. **做出 1～2 个标杆案例**：用真实交付结果建立信任，再扩大。

## 12. 开放问题

1. 垂直领域最终选哪个？
2. 付费承诺的托管方案：接第三方支付，还是先线下/模拟验证？
3. 开发者是"平台签约"还是"开放入驻"？
4. 未达标项目的资金退款时效与手续费谁承担？
5. 中标后开发者违约的追责与赔付规则？
6. 平台商业模式：抽佣 / 服务费 / 会员？（见合规，避免收益承诺）
