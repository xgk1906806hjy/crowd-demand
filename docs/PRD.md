## 1. 背景与问题

### 1.1 现状

- 用户有大量真实但分散的需求，缺少一个能被看见、能被验证、能被兑现的机制。
- 现有产品中，投票类（如各类需求墙）只解决"表达"，众筹类（如 Kickstarter）只解决"筹资"，外包/悬赏类只解决"开发"，三者彼此割裂。
- 结果：大量"高票需求"无人实现；大量开发者做了没人要的东西；出资人承担了烂尾风险。

### 1.2 核心洞察（本产品的立论基础）

参考 LEGO Ideas 的运行机制（10,000 票仅进入评审、约 1/3 过票项目被量产、官方保留最终设计权并大幅调整），得出三条设计原则：

1. **票 ≠ 钱**：投票是零成本热度，付费承诺才是真信号。投票用于发现和排序，不能作为启动开发的依据。
2. **需求 ≠ 方案**：群众擅长指出痛点，不擅长给出可执行的规格。需要一个"专业转化层"把需求翻译成可做方案。
3. **验收 ≠ 一句话满意度**：投票可被刷、开发者会拉票、烂尾难追责。必须用资金托管 + 里程碑放款 + 付费用户真实反馈来约束。

> 本产品的真正壁垒不是"把投票和钱连起来"，而是"设计一套把零成本热度转化为真实付费承诺的机制"。

## 2. 产品定位与目标

### 2.1 定位

一个聚焦垂直领域的**需求发现 + 付费承诺 + 方案竞标 + 托管交付**平台。不做全品类、不做全人群，先在一个窄口跑通闭环。

### 2.2 产品目标

| 阶段 | 目标 |
| --- | --- |
| 短期（MVP） | 验证"付费承诺"能否替代"投票热度"成为有效需求信号 |
| 中期 | 跑通 3～5 个从需求到交付的完整案例，形成可复制流程 |
| 长期 | 成为某垂直领域内"有什么需求值得做"的默认发现与验证平台 |

### 2.3 成功指标（North Star）

- **核心指标：付费承诺转化率** = 产生有效付费承诺的需求数 / 获得 100+ 票的需求数
- 辅助指标：需求数、提案数/需求、承诺金额达标率、项目按时交付率、交付后退款率、复购率

### 2.4 非目标（明确不做）

- 不做社交/社区泛内容
- 不做股权投资、返利、保本承诺类募资（见第 9 节合规）
- 不做全品类覆盖

## 3. 用户角色

| 角色 | 描述 | 核心诉求 |
| --- | --- | --- |
| 需求发起者 Requester | 提出痛点的普通用户 | 需求被看见、被解决 |
| 支持者 Backer | 投票并做出付费承诺的用户 | 用钱投票，买到真正想要的东西 |
| 开发者 Builder | 提交方案并承接开发 | 找到有真实付费意愿的项目 |
| 运营方 Operator | 平台方 | 维护规则、控风险、撮合交易 |

## 4. 核心流程（多模式）

平台支持三种发布模式，**由需求方在发布时选择**，三者共用同一套「方案征集 → 选定承接方 → 里程碑交付 → 验收放款」的后半段，只在"怎么进入可接单状态"和"钱从哪来"上不同：

| 模式 | 代码标识 | 进入可接单的方式 | 资金 |
| --- | --- | --- | --- |
| **无偿求助 / 开放认领** | `OPEN` | 发布即开放，任何认证开发者可提交方案 | 无资金托管，仅交付验收 |
| **有偿悬赏** | `BOUNTY` | 需求方**预付全额悬赏金**进托管，发布即可提交方案 | 需求方一人出资 |
| **众筹** | `CROWDFUND` | 征集投票 → 付费承诺达标 → 解锁 | 多人承诺凑钱 |

```
【悬赏 BOUNTY】  发布(预付托管) → 方案征集 → 需求方选一个 → 开发/里程碑验收 → 放款 + 剩余退回
【认领 OPEN】    发布 → 方案征集 → 需求方选一个 → 开发/里程碑验收 → 完成（无资金）
【众筹 CROWDFUND】提需求 → 投票排序 → 付费承诺(达标触发) → 提案竞标 → 开发/里程碑验收 → 放款 + 差额退回
```

三者共性：都要求**先写清需求**、都由**认证开发者提交方案**、都由**需求方最终选定**、交付过程都按**里程碑节点**验收。

### 4.1 需求生命周期状态机

变量说明：`mode` 决定走哪条支路，状态本身仍共用一套枚举，避免三套状态机分裂。

- 众筹：`草稿 → 征集中 → 承诺中 → 竞标中 → 开发中 → 验收中 → 已完成 / 已流拍 / 已退款`
- 悬赏：`草稿 → 竞标中（方案征集）→ 开发中 → 验收中 → 已完成 / 已流拍 / 已退款`
- 认领：`草稿 → 竞标中（方案征集）→ 开发中 → 验收中 → 已完成`

关键规则：
- 只有"付费承诺金额"达到目标，需求才进入开发阶段（票数仅用于排序和曝光）。
- 未达标的需求，承诺全额原路退还，不产生任何扣款。
- 每个阶段有明确时限，超时自动流转或退款。

### 4.2 三条断点的对应机制

| 断点 | 机制设计 |
| --- | --- |
| 票 ≠ 钱 | 引入"付费承诺"（预购订金，可退）；承诺金额达标才触发开发；票只决定曝光顺序 |
| 需求 ≠ 方案 | 开发者的提案必须包含：需求理解、可执行规格、报价、工期、里程碑；社区用钱+投票选方案 |
| 验收博弈 | 资金第三方托管、按里程碑放款；验收依据付费用户的确认收货 + 退款率，而非单纯满意度投票；反刷票机制 |

## 5. 功能需求

优先级：P0 = MVP 必须；P1 = 第二阶段；P2 = 后续。

### 5.1 需求模块

- **P0** 需求发布：标题、痛点描述、目标人群、期望形态、图片/附件
- **P0** 发布时选择**需求模式**（无偿认领 / 有偿悬赏 / 众筹），选定后不可更改（避免资金口径混乱）
- **P0** 需求列表与详情：按模式展示不同关键信息（悬赏金额 / 承诺进度 / 票数），支持按模式筛选
- **P0** 需求状态展示与生命周期流转
- **P1** 需求模板与发布引导（帮助群众把痛点写清楚）
- **P2** 需求合并 / 相似需求去重

### 5.2 投票与排序

- **P0** 登录用户一人一票，可对需求投"支持"
- **P0** 所有模式的需求（众筹 / 悬赏 / 无偿）都可投票；征集期与竞标期均可投，竞标期票数仅作支持表态，不触发状态流转
- **P0** 投票不要求实名（2026-11-24 变更）：登录即可投，一人一票由数据库唯一约束 `(needId, userId)` 保证；实名只在涉及资金的动作（承诺、领取资金需求）上强制
- **P0** 榜单：热度榜（票数）/ 承诺榜（金额）
- **P1** 反刷票：设备指纹、异常投票检测、新账号权重限制
- **P2** 投票理由与评论区

### 5.3 付费承诺（核心）

- **P0** 用户对需求做"付费承诺"（预购订金），写明金额
- **P0** 承诺目标进度条（已承诺 / 目标金额、剩余时间）
- **P0** 资金托管：承诺款进入第三方托管账户，未达标全额原路退回
- **P0** 达标判定：截止时间到期或提前达标 → 解锁开发阶段
- **P1** 承诺档位（如 9.9 / 49 / 99 元不同权益）
- **P1** 退出承诺机制（截止前可撤，截止后锁定）

### 5.4 开发者提案竞标

- **P0** 开发者针对已进入开发阶段的需求提交提案
- **P0** 领取不限制角色（2026-11-24 变更）：任何登录用户都可提交方案领取需求，不再要求开发者角色；无偿需求（OPEN）不要求实名，悬赏/众筹等涉及资金的需求仍要求实名
- **P0** 提案必填项：需求理解、执行规格、报价、工期、里程碑划分、过往案例
- **P0** 支持者选择提案（用付费承诺对应的"选票"），选定中标方案
- **P1** 开发者实名 / 资质认证与评分
- **P1** 提案问答与澄清区

### 5.5 开发与里程碑交付

- **P0** 里程碑拆分与节点提交（每个节点含交付物说明）
- **P0** 支持者对每个里程碑确认验收 / 提出异议
- **P0** 资金按里程碑比例释放给开发者
- **P1** 交付物托管与预览（代码仓库 / 文件 / 演示链接）
- **P2** 争议仲裁流程

### 5.6 验收与结算

- **P0** 最终验收：付费用户确认 + 退款窗口期
- **P0** 结算：达标放款，未达标退款
- **P1** 交付后评价与评分（开发者、项目双向）
- **P1** 退款率统计并进入开发者信誉

### 5.7 用户与信任

- **P0** 注册登录（手机号 / 邮箱验证码，首次登录自动注册）
- **P0** 用户名密码注册（F32）：不依赖手机/邮箱验证码，用户名 + 密码直接注册并自动登录；用户名全局唯一，注册接口按 IP 限流防批量注册
- **P0** 账号密码登录（F31）：已注册用户可在「安全设置」设置密码，之后用用户名、手机号或邮箱 + 密码登录；连续失败锁定防爆破。密码规则（2026-11-23 变更）：固定 8 位、数字开头、含大小写字母与特殊符号
- **P0** 邮箱绑定（F31）：手机号注册的用户可绑定邮箱，绑定后两种标识指向同一账号；邮箱不得与他人账号冲突
- **P0** 实名认证（涉及资金，必须）
- **P0** 用户信誉分基础版（履约次数、退款率）
- **P0** 用户控制台（F33）：实名认证、角色与信誉、我的需求、我的承诺、我的提案、发布需求等模块在控制台**页内切换展示**，点击模块不整页跳转
- **P1** 开发者认证与作品集

### 5.8 管理后台

- **P0** 需求 / 提案 / 项目审核
- **P0** 资金流水与托管状态查看
- **P0** 举报与处理
- **P1** 数据看板
- **P0** 需求线索审核：采集到的草稿需求需运营确认后才会公开发布

### 5.9 有偿悬赏需求

- **P0** 发布悬赏时填写悬赏金额（≥100 元），**发布即需预付全额**进托管，未付款视为草稿
- **P0** 悬赏需求发布后直接进入「方案征集」，不需要投票与承诺达标
- **P0** 任何登录用户可提交方案领取（不再限制开发者角色；涉及资金的需求仍需实名），需求方从中选定一个
- **P0** 选定后按里程碑交付，验收通过按节点放款
- **P0** 项目提前完成或终止时，**剩余未放款部分全额退还给需求方**（区别于众筹按承诺比例退回）
- **P1** 悬赏可选"分期托管"（按里程碑预付），降低需求方一次性资金压力
- **P2** 悬赏加价 / 延期征集

- **P0** 维护需求来源（渠道名、启用/停用），后台可切换；内置国内渠道适配器（CSDN / 微信公众号 / 掘金）与海外渠道适配器（V2EX / Hacker News / Reddit 许愿板）；~~内置演示数据源~~（v0.7 移除）

## 6. 关键机制详细说明

### 6.1 付费承诺如何工作

1. 支持者在承诺期内对某需求支付订金 → 进入托管。
2. 展示实时进度（金额、人数、剩余时间）。
3. 到期未达标 → 全额原路退回，需求转入"未达成"归档。
4. 达标 → 锁定资金，需求进入提案竞标；资金最终按里程碑释放。
5. 项目烂尾 / 严重不符 → 按规则退还剩余未释放款项。

### 6.2 方案竞标如何工作

- 一个需求可收到多个提案，公开透明。
- 支持者用其承诺金额对应的权重选择方案（避免马甲刷票）。
- 中标方案签约后进入开发；未中标提案不产生费用。

### 6.3 反刷票与反操纵

- 登录 + 一人一票（数据库唯一约束兜底）；设备 / 支付账户去重
- 实名收口到资金环节：承诺、领取涉及资金的需求、发布需求时强制实名
- 新账号冷却期，异常增长检测
- 投票与承诺分离：只有付费承诺才计入解锁

### 6.4 悬赏（有偿需求）如何工作

1. 需求方选择「悬赏」模式，填写金额与交付要求，**支付全额悬赏金**（进入托管账户）。
2. 支付成功即公开发布，进入「方案征集」，任何认证开发者可提交方案；征集中可设截止时间。
3. 需求方从方案中选定一个（**不看票数、不看承诺金额**，需求方自主决定）。
4. 选定后按里程碑交付，每个节点验收通过释放对应比例。
5. 全部完成：合同金额全额放给开发者；提前终止或缩减范围：**未释放部分退回需求方**。
6. 无开发者响应或需求方撤回：全额退回需求方，需求转「已流拍」。

> 与众筹的关键差异：出资人只有一个（需求方本人），因此**不需要选票机制**，也不存在"差额按承诺比例退回"的问题。

### 6.5 平台采集需求的边界

- 只采集**公开可见**的内容，保留来源链接，尊重目标站点的 robots 与服务条款。
- **不采集、不保存个人信息**：采集文本入库前做脱敏，手机号、身份证号、住址、账号一律剔除。
- 采集结果一律先落 `DRAFT` 草稿，**必须经运营审核**才能发布，避免把垃圾线索或不当内容直接推给用户。
- 采集用途仅限"发现需求线索"，不复制原文大段内容，不做二次分发。

## 7. MVP 范围（建议）

### 7.1 垂直领域建议

优先选择**数字化程度高、交付可验证、受众聚焦**的领域，例如：
- 办公 / 效率小工具
- 特定人群的实用 App 功能

理由：开发成本可控、交付物易确认、验收标准清晰，便于跑通闭环。

### 7.2 MVP 包含

- 需求发布（三种模式：无偿认领 / 有偿悬赏 / 众筹）+ 列表排序 + 状态流转
- 众筹路径：投票 + 应付承诺 + 托管 + 达标判定
- 悬赏路径：预付全额托管、方案征集、需求方选定
- 开发者提案 + 需求方选定 + 里程碑 + 验收 + 放款/退款
- 实名认证 + 基础后台（含需求线索审核）
- 平台需求采集的可运行版本（单一来源、定时落草稿、人工审核）

### 7.3 MVP 不包含

- 全品类、社区内容、复杂社交
- 股权投资 / 收益承诺
- 自动仲裁、AI 需求拆解（后续）
- 多来源并发采集与线索合并算法（先单来源跑通）

## 9. 合规与风险（重点）

> 公开向陌生人募资并承诺回报，在国内极易触碰非法集资 / 非法吸收公众存款红线。本产品必须在设计上规避。

必须遵守：
1. 定位为**商品/服务的预购与定制**，而非投资、募股、返利。
2. **绝不承诺固定收益、股权、保本、回报倍数**。
3. 资金进入**持牌第三方支付/银行托管账户**，平台不池资金、不自建资金池。
4. 明确披露：项目风险、交付不确定性、退款规则。
5. 实名认证 + 单笔/单人额度限制。
6. 上线前请专业律师出具合规意见，并根据属地监管要求调整。

其他风险：刷票、开发者烂尾、交付不符、需求涉侵权/违规内容 —— 均需对应风控与审核机制。

## 10. 冷启动策略

三边市场（需求方 / 出资方 / 开发者）不能同时点火，建议：

1. **先聚供给端**：邀请一批靠谱开发者或一个小而美团队，确保"有人能交付"。
2. **再聚需求端**：在一个窄领域内收集 20～30 个真实痛点，筛出 3～5 个高共鸣需求。
3. **用种子用户做付费承诺**：小范围验证"愿不愿意掏钱"，而不是先追票数。
4. **做出 1～2 个标杆案例**：用真实交付结果建立信任，再扩大。
