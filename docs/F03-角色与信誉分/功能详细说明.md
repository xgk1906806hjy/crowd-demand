## 1. 功能目标

让用户按需获得「需求发起者 / 开发者」身份，并提供一个可对外展示的信誉分，作为撮合交易时的信任参考。基础版只做**角色授予 + 基于履约/退款的信誉分计算**，不做复杂评分模型。

## 2. 用户故事

- 作为普通用户，我想要申请成为需求发起者，以便发布需求。
- 作为已实名用户，我想要申请成为开发者，以便对需求提交提案。
- 作为支持者，我想要看到开发者的信誉分与履约记录，以便判断是否值得托付。
- 边界场景：
  - 未实名用户申请开发者 → 拒绝并提示先实名。
  - 重复申请已有角色 → 幂等返回，不报错。
  - 申请运营方角色 → 拒绝（只能后台授予）。

## 3. 详细需求

### 3.1 输入

| 字段 | 类型 | 必填 | 校验规则 |
| --- | --- | --- | --- |
| role | enum | 是 | 仅允许 `REQUESTER`、`BUILDER`；`OPERATOR` 拒绝 |

### 3.2 输出

- 角色申请：`{ roles: UserRole[] }`（申请后的完整角色列表）。
- 信誉分明细：`{ score, completedProjects, totalProjects, refundedProjects, refundRate }`。

### 3.3 业务规则

1. 所有新用户默认拥有 `BACKER`（支持者）角色。
2. 可自助申请的角色：`REQUESTER`（需求发起者）、`BUILDER`（开发者）。
3. 申请 `BUILDER` 必须先完成实名（`kycStatus === VERIFIED`）。
4. `OPERATOR`（运营方）只能由后台授予，自助申请一律拒绝。
5. 角色只增不减（MVP），重复申请幂等返回当前角色。
6. 信誉分基础公式：`score = clamp(60 + 完成项目数 × 8 − 退款项目数 × 10, 0, 100)`。
7. 统计口径（以开发者身份的项目为准）：总项目数、已完成（COMPLETED）、已退款（REFUNDED）；退款率 = 退款项目数 / 总项目数（无项目时为 0）。
8. 角色变更与信誉分刷新写审计日志（`AuditAction.ROLE`）。

### 3.4 状态流转

无复杂状态机。角色为集合累加：

```
[BACKER] ──申请 REQUESTER──> [BACKER, REQUESTER]
[BACKER] ──申请 BUILDER（已实名）──> [BACKER, BUILDER]
```

### 3.5 权限

| 角色 | 可执行操作 |
| --- | --- |
| 访客 | 无 |
| 已登录用户 | 申请 REQUESTER；已实名者申请 BUILDER；查看本人信誉分 |
| 运营方 | 后台授予任意角色（归入 F18） |

## 4. 技术实现

- 涉及模块：
  - `src/domain/role/service.ts` —— RoleService（角色申请）
  - `src/domain/reputation/service.ts` —— ReputationService（信誉分计算与刷新）
  - `src/app/api/roles/apply/route.ts`
  - `src/app/api/reputation/me/route.ts`
  - `src/app/(console)/console/profile/page.tsx` —— 角色与信誉页
- 数据库变更：`AuditAction` 新增枚举值 `ROLE`；复用 `User.roles`、`User.reputationScore`、`Project`。
- 外部依赖：无。
- 资金操作：无（信誉分只读统计，不触碰资金）。

## 6. 测试要点

- 角色申请：正常申请、重复申请、非法角色、未实名申请 BUILDER。
- 信誉分：无项目时为基础分 60；有完成项目加分；有退款项目扣分；上下限收敛到 0–100。
- 权限：未登录访问 API 返回 401。
- 审计：角色变更产生 ROLE 审计记录。
