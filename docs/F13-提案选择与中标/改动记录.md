## 详细记录

### v0.1 — 2026-11-21 — 新建

- 背景：PRD 5.4 要求「发起者选定方案后进入开发」，且资金已锁定，需要生成唯一的执行项目。
- 改动内容：
  - `ProposalService.select()`：权限校验（发起者/运营方）→ 需求 BIDDING → 提案归属与状态校验 → 事务内五步操作。
  - 事务：选中提案、驳回其余 SUBMITTED、条件更新需求为 IN_PROGRESS、写状态日志、创建 Project。
  - 并发：`updateMany({ where: { id, status: BIDDING } })`，count≠1 抛 `SelectionConflict` 回滚。
  - 数据库：`Project.needId` 增加 `@unique`，保证一需求一项目。
  - API：`POST /api/needs/[id]/select-proposal`；UI：`SelectProposalButton`（二次确认）。
- 影响范围：
  - 选标后需求离开竞标，不再接受新提案。
  - 项目 `totalAmount = pledgedAmount`，`releasedAmount = 0`，供 F16 释放。
- 验证方式：
  - `npm run typecheck`：0 错误
  - `npm test`：100 用例全绿（选标 4 例）
  - `npm run build`：EXIT=0（最终全量构建 41 条路由全部生成）

### v0.2 — 2026-11-23 — 需求变更

- 背景：PRD 5.4 P0 要求「支持者选择提案（用付费承诺对应的选票）」，v0.1 只有发起者单选，`ProposalVote` 表建而未用，属于 P0 缺口。
- 设计决策：
  - 票权 = 支持者在该需求的有效承诺金额（FROZEN/LOCKED 合计，分），体现「钱越多话语权越大」。
  - 一个需求一人一票，可改票（同事务删旧票写新票）；同提案重复投为幂等。
  - 票数只作参考，最终决定权保留在发起者（防小额承诺操纵；如改为票数自动定标需先变更 PRD）。
- 改动内容：
  - `ProposalService` 新增 `voteForProposal()`、`viewerSelection()`；`listByNeed()` 聚合 `voteWeight`/`voteCount`。
  - `select()` 的需求流转改走 `transitionNeedInTx`（F06 统一入口）。
  - 新增 API `POST /api/needs/[id]/proposal-vote`；新增组件 `ProposalVoteButton`（投票/改票/已投三态）。
  - 需求详情页：提案卡片展示「支持者投票 N 人 · 票权 ¥X」，付过订金的支持者可见投票按钮（发起者本人不显示，避免自投）。
  - 内存测试库补 `proposalVote`（唯一约束、deleteMany、findFirst）与 proposal.votes 关联。
- 数据库：无 schema 变更（复用既有 `ProposalVote` 表）。
- 影响范围：需求详情页提案区、提案列表 DTO（新增 2 个字段，向后兼容）。
- 验证方式：
  - `npx vitest run`：17 文件 / 137 例全绿（本功能新增 8 例投票用例）
  - `npx tsc --noEmit`：0 错误
  - `npm run build`：EXIT=0（30 条路由，新增 proposal-vote）
