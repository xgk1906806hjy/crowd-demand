## 1. 功能目标

让需求方**自己出钱**把需求做出来：发布时预付全额悬赏金进托管，开发者看到方案征集直接提方案，需求方选一个开工，按里程碑验收放款，没花完的退回自己。

解决 v0.1 定位错误导致的断点——原实现要求所有需求先凑够票数、再由他人付费承诺达标，导致"我出钱找人做"这种最普通场景无法发布。

## 2. 用户故事

- 作为需求方，我想填一个金额把需求悬赏出去，以便马上有开发者来报价，而不是先攒票和承诺。
- 作为开发者，我想直接对悬赏需求提方案，以便不用等众筹达标就能接活。
- 作为需求方，我想在没人接单或我改主意时把钱全额拿回来，以便没有资金风险。
- 边界场景：① 悬赏金额付到一半支付失败 → 需求保持草稿，不公开；② 已有方案征集但无开发者响应 → 需求方可撤回并全额退款；③ 项目只完成部分节点就终止 → 已放款部分不退，剩余全额退回需求方。

## 3. 详细需求

### 3.1 输入

发布需求时新增：

| 字段 | 类型 | 必填 | 校验规则 |
| --- | --- | --- | --- |
| mode | enum | 是 | `OPEN` / `BOUNTY` / `CROWDFUND`，发布后不可更改 |
| bountyAmount | 金额字符串（元） | BOUNTY 必填 | ≥100 元、≤100 万元，转整数分入库 |
| bountyDays | int | 否 | 方案征集期 1~60 天，默认 14 天 |

### 3.2 输出

- 发布结果返回 `id`、`status`、`mode`、`bountyAmount`（分）、`paymentRef`。
- 列表/详情返回模式标签、"悬赏 ¥X"、征集剩余天数；众筹需求保持原有承诺进度展示。

### 3.3 业务规则

1. **模式决定入口**：`CROWDFUND` 走原五步（征集→承诺→达标）；`BOUNTY` 与 `OPEN` 支付/发布成功即进入 `BIDDING`（方案征集），**跳过投票与承诺期**。
2. **悬赏必须预付全款**：`BOUNTY` 未支付成功不得公开（保持 `DRAFT`）。支付与记账在同一事务语义下：先 `gateway.charge` 拿回执，再写 `BountyEscrow` 与账本两条流水。
3. **资金口径**：悬赏金记在需求方的虚拟账户（BACKER）→ ESCROW，`bizType=BOUNTY`；不动 `Pledge` 表，避免与承诺混算。
4. **选标**：`BOUNTY`/`OPEN` 下由**需求方本人**选定方案，不参与 F13 的承诺票权计算；同一需求只能选一个。
5. **放款**：复用里程碑比例放款，从 ESCROW 放给开发者（`payout:{milestoneId}`）。
6. **退余款**：项目结束（完成或终止）时，ESCROW 中该悬赏的剩余额度全额退回需求方（`bountyrefund:{needId}`）；众筹需求仍按承诺比例退回，两者不混用。
7. **流拍退款**：征集期结束无方案 / 需求方撤回 → 全额退回，需求置 `REFUNDED`。
8. **幂等**：支付幂等键 `bounty-charge:{needId}`，退款 `bountyrefund:{needId}`，放款 `payout:{milestoneId}`，重复调用不重复记账。

### 3.4 状态流转

```
CROWDFUND: DRAFT → COLLECTING → PLEDGING → BIDDING → IN_PROGRESS → ACCEPTING → COMPLETED
BOUNTY   : DRAFT → BIDDING → IN_PROGRESS → ACCEPTING → COMPLETED
           BIDDING → FAILED → REFUNDED（无人响应/需求方撤回）
           IN_PROGRESS → FAILED → REFUNDED（终止，退未放款部分）
OPEN     : DRAFT → BIDDING → IN_PROGRESS → ACCEPTING → COMPLETED（无资金）
```

`canTransition` 增加 mode 参数：`DRAFT → BIDDING` 仅对 `BOUNTY`/`OPEN` 放行。

### 3.5 权限

| 角色 | 可执行操作 |
| --- | --- |
| 需求发起者 | 选择模式发布、查看征集、选定方案、撤回（征集期）、终止（开发中） |
| 支持者 | 众筹模式下可投票与承诺；悬赏/认领模式下无参与入口 |
| 开发者 | 对悬赏/认领需求提交方案（需认证） |
| 运营方 | 审核、强制终止、查看托管与流水 |

## 4. 技术实现

- 涉及模块：`src/domain/need/state-machine.ts`（mode 感知流转）、`src/domain/need/service.ts`（发布分流）、`src/domain/bounty/service.ts`（新建：托管、退款、结算余额）、`src/domain/proposal/service.ts`（选标分支）、`src/domain/payout/service.ts`（退余款）、`src/app/api/needs/route.ts`、`src/app/(console)/console/needs/new/page.tsx`
- 数据库变更：`Need.mode`（枚举 `NeedMode`，默认 `CROWDFUND`）、`Need.bountyAmount BigInt`、`Need.bountyDeadline DateTime?`；新增 `BountyEscrow`（needId、amount、refundedAmount、paymentRef、状态）
- 外部依赖：`PaymentGateway.charge/refund`（当前 Mock）
- ⚠️ 资金操作全部走 `postTransfer` + 事务 + 幂等键，禁止直接改余额

## 5. 验收标准

- [ ] 悬赏需求发布 → 托管记账 → 进入方案征集，一步可用
- [ ] 未支付成功的悬赏不公开（无 `publishedAt`）
- [ ] 开发者可对悬赏需求提交方案，需求方选定后建项目
- [ ] 里程碑验收按比例放款，账本借贷平衡
- [ ] 撤回/流拍全额退款，托管余额归零
- [ ] 众筹需求行为完全不变（回归通过）
- [ ] 单元测试通过（含幂等、退款、余额不足、模式越权）

## 6. 测试要点

1. 悬赏发布：金额不足 100 元、超额、非实名、支付失败 → 各有明确错误且无脏数据。
2. 幂等：同 `bounty-charge` 重复调用只产生一条托管与两条流水。
3. 模式越权：`CROWDFUND` 需求直接跳 `BIDDING` 必须被拒（防止绕过众筹门槛）。
4. 退款：撤回后退款一次，二次调用幂等；ESCROW 余额不为负。
5. 选标：非需求方选标被拒；已选过再选被拒。
6. 结算：只完成 1/2 节点即终止 → 已放 50%，余 50% 退回需求方，账本平衡。
