## 1. 功能目标

当全部里程碑释放完毕，项目进入最终结算：项目完成、需求完成；若实际报价低于托管总额，剩余资金按承诺比例原路退回支持者，一分钱不留在平台。

## 2. 用户故事

- 作为支持者，我想在项目完成后拿回多付的差额，以便不被多收钱。
- 作为发起者，我想项目结束后看到「已完成」状态与结算结果。
- 边界场景：
  1. 报价 = 托管总额 → 无差额，不产生退款。
  2. 差额除不尽 → 最后一笔承接余数，总额精确。
  3. 仍有节点未释放 → 不触发结算。

## 3. 详细需求

### 3.1 输入

| 字段 | 说明 |
| --- | --- |
| projectId | 项目 |
| needId | 需求 |
| totalAmount | 托管总额（分） |
| quote | 中标报价（分） |
| actorId | 触发结算的验收人 |
| refunds | 外部退款回执（pledgeId → 托管方流水号），事务外已调用网关 |
| provider | 实际支付适配器标识（禁止硬编码 mock） |

### 3.2 输出

`{ refunded }`（退款总额，分）

### 3.3 业务规则

1. **触发条件**：该节点验收后，项目中不存在非 `RELEASED` 的节点。
2. **差额计算**：`leftover = max(totalAmount − quote, 0)`。
3. **按比例退款**：`share_i = floor(leftover × pledge_i / totalPledged)`，最后一笔承接余数。
4. **承诺终态**：全部承诺置为 `RELEASED`（已使用），部分退款记录在账本与 `PaymentOrder`（type=REFUND）。
5. **状态联动**：项目 `COMPLETED`、需求 `ACCEPTING → COMPLETED`，写状态日志。
6. **审计**：放款写 PAYOUT，退款写 REFUND。
7. **外部退款走适配器**：差额退款前按 `settle:{pledgeId}` 调用 `PaymentGateway.refund`，回执写入 `PaymentOrder(REFUND)`；任何一笔调用失败则不进入结算事务，避免「账上退了、钱没退」。
8. **托管归零校验**：结算后托管余额应满足「放款总额 + 退款总额 = 托管总额」，余额不足由账本护栏拦截。

### 3.4 状态流转

```
ACCEPTING ──全部节点释放──→ COMPLETED
项目：IN_PROGRESS/ACCEPTING ──结算──→ COMPLETED
```

### 3.5 权限

| 角色 | 可执行操作 |
| --- | --- |
| 需求发起者 | 验收最后一个节点（触发结算） |
| 系统 | 自动结算 |
| 运营方 | 代为验收触发 |

## 4. 技术实现

- 涉及模块：`src/domain/payout/service.ts`（`settleProjectInTx`）、`src/domain/milestone/service.ts`（结算前的外部退款调用）
- 事务：与最后一个节点的放款同一事务；外部网关调用在事务之前
- 幂等：退款键 `settle:{pledgeId}`；Payout 键 `payout:{milestoneId}`；网关按 reference 幂等
- 资金：托管账户在结算后应归零（放款 + 退款 = 托管总额）
- ⚠️ 已知限制：外部退款与结算事务之间存在极窄竞态（同一最后节点被并发验收）；当前以单一发起者验收 + 节点原子认领规避，接持牌机构后改为异步对账

## 5. 验收标准

- [x] 差额按承诺比例分配，除不尽由最后一笔承接

- [x] 结算后需求 `ACCEPTING → COMPLETED` 走状态机唯一入口
- [ ] 结算对账报表（F19）

## 6. 测试要点

1. 托管 100000、报价 80000、承诺 60000/40000 → 退款 12000/8000。
2. 报价等于托管额 → 无退款流水。
3. 结算后需求 COMPLETED、项目 COMPLETED、日志齐全。
4. 托管余额 = 放款总额 + 退款总额。
