## 1. 方案总原则

1. **按功能点开发，一功能一档案**：PRD 中每个 P0/P1/P2 功能点对应一个唯一编号 `Fxx`，每个功能在 `docs/` 下建一个目录，内含 `功能详细说明.md` 和 `改动记录.md`（规则见 `AGENTS.md`）。
2. **资金正确性优先**：涉及钱的功能（承诺、托管、放款、退款）必须走同一套账本 + 事务，禁止各处直接改余额。
3. **状态机集中管理**：需求生命周期、承诺状态、提案状态、里程碑状态由领域层统一流转，禁止在 UI 层判断状态。
4. **MVP 先跑通闭环**：先用 Mock 支付/托管适配器跑通全流程，再接真实持牌机构，避免合规与接口阻塞开发。
5. **可验证交付**：每个功能必须有单元测试，资金与状态流转功能必须有集成测试。

## 3. 开发阶段与依赖关系

```
M1 原型（可选，快速验证交互）
   └─ 可点击原型，覆盖 F04→F05→F09→F12 主流程

M2 MVP（P0 全量，目标：跑通 1 个真实项目）
   ├─ 阶段 A 基础：F01 → F02 → F03
   ├─ 阶段 B 需求：F04 → F05 → F06 → F07 → F08
   ├─ 阶段 C 资金：F09 → F10 → F11   ← 核心链路，重点测试
   ├─ 阶段 D 提案：F12 → F13
   ├─ 阶段 E 交付：F14 → F15 → F16 → F17
   └─ 阶段 F 后台：F18 → F19 → F20

M3 迭代（P1）：F21 ~ F27
M4 后续（P2）：反仲裁、去重等
```

**关键路径**：F02 实名认证 → F09 付费承诺 → F10 资金托管 → F16 放款 → F17 结算。这条链路上任一功能延期，都会阻塞 MVP 闭环，优先保障。

## 4. 分层架构

```
┌─────────────────────────────────────────────┐
│ 表现层  Next.js App Router / React 组件       │  UI、表单、状态展示
├─────────────────────────────────────────────┤
│ 接口层  Route Handlers / Server Actions      │  校验、鉴权、DTO
├─────────────────────────────────────────────┤
│ 领域层  services + 状态机 + 账本规则          │  业务规则、事务边界  ★核心
├─────────────────────────────────────────────┤
│ 数据层  Prisma Repository / PostgreSQL       │  持久化、事务、行锁
├─────────────────────────────────────────────┤
│ 外部适配  PaymentGateway / SMS / OSS / Redis  │  可替换的外部依赖
└─────────────────────────────────────────────┘
```

- **依赖方向**：上层依赖下层，领域层不直接依赖具体支付/短信实现（通过接口注入）。
- **事务边界**：资金相关操作（F09/F10/F16/F17）在领域层用数据库事务包裹，账本流水与业务状态在同一事务内提交。

## 5. 三个关键机制的技术方案

### 5.1 需求状态机（F06）

```
草稿 DRAFT
  → 征集中 COLLECTING（发布后进入）
  → 承诺中 PLEDGING（达到最低票数门槛，进入付费承诺期）
  → 竞标中 BIDDING（承诺达标，锁定资金）
  → 开发中 IN_PROGRESS（中标方案确定）
  → 验收中 ACCEPTING（里程碑提交）
  → 已完成 COMPLETED / 已流拍 FAILED / 已退款 REFUNDED
```

- 状态流转用集中式 `NeedStateMachine`，每次流转写入 `NeedStatusLog`（谁、何时、从何状态到何状态、原因）。
- 定时任务（BullMQ）检查：承诺期到期未达标 → 自动 `FAILED` 并触发全额退款。

### 5.2 资金账本（F10/F16/F17）

- 不直接存"用户余额"，而是用**复式账本**：每笔资金变动记一条 ledger（账户、方向、金额、业务单号、余额快照）。
- 三类虚拟账户：支持者承诺账户、平台托管账户、开发者收款账户。
- 承诺 = 从支持者账户冻结到托管账户；放款 = 从托管账户转到开发者；退款 = 从托管退回支持者。
- 所有金额用**整数分**存储，禁止浮点。
- 幂等键：每笔资金操作带唯一 `idempotencyKey`，防止重复扣款/放款。

### 5.3 反刷票前置约束（F07，P1 增强）

- MVP：实名用户一人一票，数据库唯一约束 `(need_id, user_id)`。
- P1：叠加设备指纹 + 新账号冷却期 + 异常增长告警（F22）。

## 7. 合规红线（开发时强制）

1. 所有资金文案用"预购订金/定制款"，禁止出现"投资、收益、回报、股权、保本"等词。
2. 平台不自建资金池，托管走适配器的持牌账户；MVP 阶段 Mock 适配器只在测试/演示环境使用。
3. 单笔/单人额度上限做成配置，默认开启。
4. 所有资金操作写审计日志，不可物理删除。
