## 1. 功能目标

给用户一个低成本的内容治理入口：发现虚假需求、抄袭提案或违规账号可以举报；运营方在后台判定成立与否，形成可追溯的处理记录。

## 2. 用户故事

- 作为普通用户，我想举报明显虚假或违规的需求，以便保护其他人。
- 作为运营方，我想看到待处理举报并标记成立/不成立，以便闭环。
- 边界场景：
  1. 举报原因只有两个字 → 拒绝，提示至少 10 字。
  2. 同一用户重复举报同一对象 → 冲突提示，避免刷举报。
  3. 已处理的举报再次处理 → 提示已处理。

## 3. 详细需求

### 3.1 输入

| 字段 | 类型 | 必填 | 校验规则 |
| --- | --- | --- | --- |
| targetType | NEED/PROPOSAL/USER | 是 | 枚举 |
| targetId | string | 是 | 非空 |
| reason | string | 是 | 10-1000 字 |
| action | RESOLVE/REJECT | 处理时必填 | 枚举 |

### 3.2 输出

- 举报：`{ id, status: PENDING }`
- 处理：`{ status: RESOLVED | REJECTED }`

### 3.3 业务规则

1. **登录才能举报**；同一用户对同一对象只能有一条 `PENDING` 举报。
2. **处理权限**：仅 `OPERATOR`。
3. **一次处理**：仅 `PENDING` 可处理，处理人写入 `handledBy`。
4. **审计**：创建与处理均写 `AuditLog`（ADMIN）。
5. **不自动处置**：MVP 仅记录判定结果，不自动下架内容（P1 增加联动）。

### 3.4 状态流转

```
PENDING ──成立──→ RESOLVED
PENDING ──不成立──→ REJECTED
```

### 3.5 权限

| 角色 | 可执行操作 |
| --- | --- |
| 未登录 | 不可举报 |
| 已登录用户 | 提交举报、查看提交结果 |
| 运营方 | 查看待处理列表、判定成立/不成立 |

## 6. 测试要点

1. 原因 <10 字拒绝。
2. 非法 targetType 拒绝。
3. 重复 PENDING 举报返回 CONFLICT。
4. 处理写入 handledBy 与状态。
5. 已处理再处理返回 INVALID_STATE。
