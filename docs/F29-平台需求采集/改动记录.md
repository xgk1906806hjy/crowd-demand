### v0.4.1 — 2026-11-24 — 优化（真实数据上线后修正）

- 触发原因：真实渠道首轮采集后榜单出现两类质量问题：① 多条标题共用的泛化句式（"有没有推荐的工具"）被关键词相似度聚成一条 12 次提及的"大杂烩"；② 工具盘点/推介文因摘要出现"痛点"二字被误判为需求（如"干货满满！推介几款 Mac 软件，解决你的痛点"）。
- 聚合收口（`keywords.ts`）：
  - 新增 `isGenericTitle`：去掉需求句式与万能词（工具/软件/推荐/办法/方案/东西…）后，剩余具体信息不足 4 字即判为泛化标题，**不参与聚合**（既不用标题指纹，也不用关键词）。
  - 新增 `meaningfulKeywords`：聚合前剔除万能词二元组与含「的/了/是」的滑窗虚词（"用的""的在"），只保留主题词。
  - `isSamePain` 改为基于有效关键词计算，阈值仍为交集 ≥3 且占比 ≥0.4。
- 需求信号收紧：`痛点` 单独出现不再算需求，仅匹配"痛点在于/是/："自述句式；新增"求助/急求/有偿求"。
- 微信渠道：检索词从 6 个降为 3 个、请求间退避 500ms；拿到页面却无结果块时抛错（后台可见"可能被限流或页面改版"），不再静默 fetched=0。
- 冒烟更新：`smoke-f29.sh` 改为校验"来源含国内渠道""演示数据源已移除"，停用来源需全量停用后才断言 created=0，丢弃目标只挑 COLLECTED 线索以保证可重复执行；结果 25 项全过。
- 数据修正：部署后清空 `ClueMention`/`DemandClue` 并按新规则重建；线上采集一轮候选 CSDN 111 + 掘金 113 + HN 74，入库 111 条线索、提及人数普遍为 1（真实渠道跨平台重复表达有限，聚合会随新表述逐步发生）。

### v0.5 — 2026-11-24 — 优化（大模型实测后修正）

- 背景：接入 `gpt-6.2-sol` 后首次全量采集发现两类问题——① 40 条/批串行调用单批超过 30 秒默认超时，整批降级回规则判定；② 规则粗筛（`looksLikeDemand`）排在模型之前，中文技术社区大量「如何实现 XX」式真实提问被提前丢弃，榜单几乎全被 HN 英文 Ask 帖占据。
- 改动内容：
  - 大模型整合（`src/domain/clue/enrich.ts`）：`MAX_BATCH=40` 不变，`MAX_TOTAL` 提到 240，改为**3 路并发**分批，单批超时 30s → 120s；提示词明确「介绍/教程/评测/招聘不算需求，只有作者自述诉求才算」，并要求**一律输出简体中文标题**（英文原文翻译压缩）。
  - 采集编排（`src/domain/clue/collect.ts`）：启用大模型时，规则只负责剔除强广告/招聘噪声（新增 `isLikelyNoise`），其余候选全部交给模型判定；未配置模型时仍走原规则链路。
  - CSDN 适配器（`src/infrastructure/clue/csdn.ts`）：同时检索 `t=ask`（ask.csdn.net 问答，真实提问）与 `t=blog`（前 3 个检索词补充），ask 优先。
  - nginx（`deploy/nginx.conf`）：`/api/` 的 `proxy_read_timeout` 60s → 300s，避免手动/定时采集在模型整合阶段被网关截断（容器内 bind mount 需重启 nginx 容器才读到新内容）。

### v0.8 — 2026-11-25 — 改造（两段式：10 分钟采集 + 每小时聚合分析）

- 需求：用户要求改为「每 10 分钟挖一次各大社交平台/抖音快手公开搜索页，挖掘方式也含大模型搜索；每小时把约 6 轮数据交大模型分析，提取重复次数最多、有意义的需求」。三问确认口径：抖音/快手先试公开搜索页（不采购接口、不绕过签名）；「大模型搜索」= 模型生成检索词 + 联网搜索 API 两者都做；小时分析结果并入现有热榜（不新增独立简报页）。
- 实现：
  - **schema**：新增 `ClueCandidate`（单轮采集候选缓冲区，`sourceKey/externalId/title/excerpt/url/authorKey/mentionedAt/roundId/fetchedAt/usedAt`，`@@unique([sourceKey,externalId])`，索引 `fetchedAt`/`usedAt`）与 `ClueQuery`（模型检索词，`query/origin/createdAt`，`@@unique([query])`）；补丁 `prisma/patches/2026-11-25-f29-hourly.sql`（幂等 CREATE TABLE IF NOT EXISTS + 索引）。
  - **env**：`CLUE_SOURCES` 默认 `csdn,weixin,juejin,douyin,kuaishou,hn`；`CLUE_INGEST_INTERVAL_MIN` 60→**10**；新增 `CLUE_ANALYZE_INTERVAL_MIN`(60)、`CLUE_ANALYZE_MAX_ITEMS`(200)、`CLUE_SEARCH_API_URL/KEY`(可选)、`CLUE_ROUND_INGEST`(true/false，默认 false)。
  - **新适配器**：`douyin.ts`（公开搜索页，解析 `window._ROUTER_DATA` 递归找 `aweme_info`，纯函数 `parseDouyin`）、`kuaishou.ts`（解析 `window.__APOLLO_STATE__`，纯函数 `parseKuaishou`）、`websearch.ts`（POST 通用搜索 API，`parseSearchResponse` 兼容 `data/results/organic_results/web.value/webPages.value`）；三者失败均抛明确错误，由来源级隔离兜住。

  - **llm-search**：`QUERY_PROMPT`（4–12 字自然短语、覆盖多场景、排除盘点/教程/排行）+ `parseQueryList` + `generateQueries`（取最近 60 条线索标题作语感样本，与库内已有词去重后 `createMany`）+ `listActiveQueries`（最近 24 小时最多 8 条）。
  - **analyze.ts（核心）**：`analyzeHourly` 节流键 `CronState("clue-hourly")`；取窗口内 `usedAt=null` 候选（上限 200）；`CLUSTER_PROMPT` 两步（先筛真需求、再跨条合并，同品类同用途才合并、一条只归一组）+ 输出 `canonicalTitle/memberIndexes/score/reason`；`parseClusters` 纯函数（去重成员、越界丢弃）；`clusterByRules` 规则兜底；门槛 **成员≥2 或 score≥80**；每组以 `canonicalTitle` 覆盖成员标题后调 `ClueService.ingest(batch,{requireDemandSignal:false})`，让同组聚成一条线索（`mentionCount` 自然反映重复度）；消费完置 `usedAt` 并写 `CronState`；每轮顺带刷新 10 个检索词（`newQueries`）。
  - **collect.ts**：先取模型词 → 建来源 → 排除 `ClueMention`/`ClueCandidate` 已见 → 单轮判定（`refineClues`）→ 按 `roundId`（ISO 截到分钟）写 `ClueCandidate`；`CLUE_ROUND_INGEST=true` 时保留旧「轮次直接入库」行为可回退。
  - **cron 路由**：job 扩为 `expire|clues|clue-hourly|all`，`all` 依次 expire → clues → hourly，`force` 透传。

### v0.8.1 — 2026-11-25 — 修正（单轮耗时与候选滞留）
