## 1. 功能目标

平台不只等用户上门发需求：定时抓取外部公开渠道（社区/社媒）里的需求表达，把同一痛点的多次提及聚合成一条「需求线索」，按**提及人数**排出热榜公开展示，让「最多人想要什么」一目了然。

## 2. 用户故事

- 作为访客，我想看「提及热榜」，知道当下最多人反复提的痛点是什么，以及原始出处。
- 作为运营，我想启停采集来源、手动触发采集、逐条收录或丢弃线索。
- 作为需求方，我看到热榜上的痛点后可以到控制台把它发布成正式需求，进入投票/承诺流程。
- 边界场景：
  1. 同一帖子被重复采集 → 幂等跳过，不重复计数。
  2. 同一作者发多帖 → 次数累加，人数只算 1。
  3. 单个渠道超时/被封 → 该渠道跳过并记录错误，不影响其他渠道。
  4. 摘要里出现手机号/身份证/邮箱 → 入库前替换为「[已脱敏]」。

## 3. 详细需求

### 3.1 输入

来源适配器返回 `ClueItem`：

| 字段 | 说明 | 校验 |
| --- | --- | --- |
| sourceKey | 渠道 key（csdn / weixin / juejin / v2ex / hn / reddit；mock 已于 v0.4 移除） | 来源须存在且启用 |
| externalId | 来源侧唯一 ID | 与 sourceKey 联合唯一，幂等 |
| title | 帖子标题 | 非空，截断 120 字 |
| excerpt | 公开正文摘要 | 脱敏 + 截断 300 字 |
| url | 原文链接 | 展示用 |
| authorId | 来源侧作者标识 | 仅生成 sha256 哈希后丢弃 |
| mentionedAt | 提及时间 | 非法时间回退当前时间 |

### 3.2 输出

- 公开 `GET /api/clues/top` 与页面 `/trending`（需求热榜，2026-11-24 由「提及热榜」更名）：按提及人数 > 提及次数 > 最近提及时间排序，附来源样本（≤3 渠道）；**首页展示前 10 条**并链接完整热榜。
- 运营 `GET /api/admin/clues`：全部线索 + 来源列表；`POST /api/admin/clues/[id]/review`（FEATURE/DISCARD）、`POST /api/admin/clues/collect`（强制采集）、`POST /api/admin/clues/sources`（启停）。
- cron 响应含 `clues` 摘要（v0.8）：`{ ran, reason?, sources: {key: {fetched|error}}, candidates, llmQueries, llm: {applied, dropped, provider}, ingest? }`；`hourly` 摘要：`{ ran, reason?, candidates, clusters, avgRepeat, ingest, provider, newQueries, ranAt }`。

### 3.3 业务规则

1. **需求信号过滤**：中文（求推荐/有没有/想找/谁能做…）与英文（I wish there was / somebody make / is there a tool…）模式命中才入库。
2. **幂等**：`(sourceKey, externalId)` 数据库唯一约束；重复采集跳过；并发冲突（P2002）按跳过计。
3. **聚合**：标题指纹相同或有效关键词交集 ≥3 且交集/较小集合 ≥0.4 → 合并到既有线索；模板短语（有没有/能把/自动/整理成/的工具…）先剥离再提取中文二元组；**v0.4 收紧**：泛化标题（去掉句式与「工具/软件/推荐/办法」等万能词后剩余不足 4 字，如「有没有推荐的工具」）不参与聚合；聚合改用有效关键词（剔除万能词与「的/了/是」虚词二元组），避免不同主题被同一句式骨架误合并。
4. **计数口径**：`mentionCount` = 提及总次数；`mentionerCount` = 按作者哈希去重的人数（榜单第一排序键）。
5. **隐私红线**：摘要脱敏（手机号/18 位身份证/邮箱），作者只存 `sha256(sourceKey:authorId)`，不存平台原始 ID。
6. **审核状态机**：COLLECTED → FEATURED（收录）/ DISCARDED（丢弃，终态）；丢弃后热榜隐藏、不再合并新提及（新提及另立线索）。
7. **两段式节流（v0.8）**：cron 每 5 分钟触发；第一段采集按 `CLUE_INGEST_INTERVAL_MIN`（默认 **10 分钟**）节流，只写候选缓冲区；第二段聚合按 `CLUE_ANALYZE_INTERVAL_MIN`（默认 **60 分钟**）节流，消费窗口内约 6 轮候选后统一入库。运行状态分别存 `CronState` 的 `clue-ingest` / `clue-hourly`；运营手动触发跳过节流。
8. **审计**：每次有效入库与审核/来源操作写 `AuditLog`（action=ADMIN）。
9. **采集范围（v0.4 / v0.8）**：只取各站**公开检索结果卡片**（标题、摘要、链接、时间、渠道作者名），不进入文章正文、评论区，不使用登录态、不绕过验证码/签名。国内已接入 CSDN、微信公众号（微信搜狗结果页）、掘金；**v0.8 新增抖音、快手公开搜索页**（`www.douyin.com/search/*`、`www.kuaishou.com/search/video`，解析 `window._ROUTER_DATA` / `window.__APOLLO_STATE__`，需 JS 渲染或签名大概率解析不到，按合规不绕过，失败仅记来源级错误）与**通用联网搜索**（配置 `CLUE_SEARCH_API_URL/KEY` 后启用）。微博/小红书/知乎/贴吧仍不可抓取。
10. **两个检索词来源 + 轮次轮换（v0.8）**：固定中文需求词库（`shared.ts`）+ 模型每小时生成的检索词（`ClueQuery` 表，取最近 24 小时最多 8 条）。检索词要求 4–12 字自然短语、覆盖多场景，剔除盘点/教程/排行/合集类词。**每轮只下发 `CLUE_QUERIES_PER_ROUND`（默认 4）条，按轮次序号在整份词表上滑动**——全量下发会让每轮重抓同一批结果页、把数百条候选送进模型，单轮耗时可达 20 分钟以上，与 10 分钟节奏冲突。
11. **每小时聚合分析（v0.8）**：取全部未消费的 `ClueCandidate`（最旧优先，单次上限 `CLUE_ANALYZE_MAX_ITEMS`=200，超出的留给下次继续消费，不按时间窗截断以免候选永久滞留），**按 15 条一批**分批交模型做两步处理——先筛真需求、再跨条合并（同品类同用途才合并，只品类相同不合并，一条只归一组），输出 `canonicalTitle / memberIndexes / score / reason`，各批结果按规范化标题合并；接受门槛为**成员 ≥2 或 score≥80**；每组用 `canonicalTitle` 覆盖成员标题后走既有聚合入库，`mentionCount` 自然反映重复度。主模型 content 为空/超时时自动切备用模型；全部批次失败才退化为规则聚类（`isSamePain` + 关键词交集）。消费完的候选置 `usedAt`。
10. **可选大模型整合（v0.4 / v0.5 / v0.7）**：`LLM_BASE_URL/LLM_API_KEY/LLM_MODEL`（+ 可选 `LLM_WIRE_API=chat|responses`）齐备时，采集后把候选按 **10 条一批**、4 路并发交由模型判定是否真实需求并给出规范化中文标题（英文原文标题再补一次翻译），再走聚合入库。发往模型的仅脱敏后的标题与摘要。线上实测：主模型 `sensenova-6.8-flash-lite`（`https://token.sensenova.cn/v1`，`chat` 协议），备用模型 `gpt-6.1-terra`（`https://cn.fluxtoken.ai/v1`，`responses` 协议）；主模型报错/超时自动切备用，cron 响应 `llm.provider` 可核对本轮实际使用的模型。
    - **v0.7 判定口径（质量优先）**：提示词先跑「非需求黑名单」（盘点/清单/排行榜、资讯与发布、自述自研自荐、教程/攻略/源码解析、报错与实现求助、学习资料、作业考试毕设、招聘面经、情绪与观点、软件具体操作提问），命中即判否；未命中再核对三条正向条件（本人诉求 / 缺的是可复用产品 / 能说清用途），拿不准判否。例外条款：标题本身是「求推荐/有没有/想找+具体工具品类」且品类明确时，即使未写场景也判是，避免误杀。
    - **自证与置信分**：判为需求必须输出 `reason`（缺什么、用来做什么）；本地要求 `score >= 75` 且 `reason` 非空，否则按非需求剔除。模型漏判该条时走规则兜底（有需求句式且非推介标题才保留）。
    - **批次与降级**：主模型是 reasoning 模型，单条先产出上千 token 思维链，40 条/批会耗尽输出预算导致 `content` 为空；因此压到 10 条/批并显式设置 `max_tokens=4000`。单批失败不再整批放行，而是降级为「有需求句式且非推介/盘点标题」的规则筛选，避免模型故障时噪声灌入榜单。

### 3.4 状态流转

```
COLLECTED ──运营收录──→ FEATURED
COLLECTED / FEATURED ──运营丢弃──→ DISCARDED（终态）
```

## 4. 技术实现

- 领域层：`src/domain/clue/keywords.ts`（纯函数：提取/匹配/过滤/脱敏）、`service.ts`（入库/榜单/审核）、`collect.ts`（第一段编排：模型检索词 + 候选缓冲 + 节流）、`analyze.ts`（第二段：小时聚合、`parseClusters`/`clusterByRules`）、`llm-search.ts`（`QUERY_PROMPT`/`parseQueryList`/`generateQueries`/`listActiveQueries`）、`enrich.ts`（可选大模型判定与标题归一，导出 `callLlm` 供复用）
- 适配器：`src/infrastructure/clue/{types,shared,csdn,weixin,juejin,douyin,kuaishou,websearch,v2ex,hn,reddit,factory}.ts`，零新增 npm 依赖（原生 fetch + AbortSignal.timeout）；`shared.ts` 提供统一检索词、HTML 清洗、时间归一、去重；`factory.ts` 以 `createClueSources(extraQueries)` 把固定词与模型词去重后下发
- API：`/api/clues/top`、`/api/admin/clues*`、`/api/internal/cron`（job=expire|clues|clue-hourly|all, force）
- 前端：`/trending` 需求热榜、首页热榜前 10 区块、`/admin/clues` 审核面板；顶部导航精简（移除需求广场/承诺榜/热榜入口，经首页到达）
- 数据库：`DemandSource` / `DemandClue` / `ClueMention` / `CronState` + `ClueStatus` 枚举；**v0.8 新增** `ClueCandidate`（候选缓冲，`@@unique([sourceKey,externalId])`）与 `ClueQuery`（模型检索词，`@@unique([query])`）；增量补丁 `prisma/patches/2026-11-24-f29-clues.sql`、`2026-11-25-f29-hourly.sql`（均幂等）
- 配置：`CLUE_SOURCES`（默认 `csdn,weixin,juejin,douyin,kuaishou,hn`）、`CLUE_INGEST_INTERVAL_MIN`（10）、`CLUE_ANALYZE_INTERVAL_MIN`（60）、`CLUE_ANALYZE_MAX_ITEMS`（200）、`CLUE_ROUND_INGEST`（false）、`CLUE_FETCH_TIMEOUT_MS`（15000）、可选 `CLUE_SEARCH_API_URL` / `CLUE_SEARCH_API_KEY`；可选 `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL` / `LLM_WIRE_API`
- 资金操作：无（本功能不触碰资金）

## 6. 测试要点

1. 合并：4 种措辞的同一痛点 → 1 条线索、mentionCount=4、mentionerCount=4。
2. 幂等：同批数据二次入库 created=0/merged=0/skipped=全部。
3. 同作者多帖：次数 2、人数 1。
4. 非需求文本过滤；停用来源跳过。
5. 脱敏断言：手机号/身份证/邮箱不出现在库内摘要；authorKey 为 64 位哈希。
6. 排序与丢弃：热榜按人数排序；DISCARD 后不上榜、不合并新提及。
7. 节流：间隔内 throttled，force 跳过，过期恢复。
8. 渠道解析：CSDN 去 `<em>` 高亮、微信搜狗提取标题/摘要/公众号/时间并补全链接、掘金读取 `result_model.article_info`；异常结构返回空数组。
9. 大模型整合：未配置时零调用原样返回；配置后剔除伪需求、替换规范化标题；接口失败降级原数据；载荷不含作者与链接。
10. 聚合收口：泛化标题（「有没有推荐的工具」）不参与合并；不同主题共用句式（在线画图 vs 在线剪辑）不合并；同一具体痛点不同措辞仍合并。
11. 需求信号：工具推介/盘点文（"推介几款 Mac 软件，解决你的痛点"）不算需求；自述痛点、求取、求助仍算需求。

## 8. 风险与边界

- 国内渠道均为公开检索结果页/接口，可能限流、改版或返回空：来源级失败隔离 + 超时控制，解析失败返回空不影响其他渠道；改版时需更新 `parseXxx` 正则/字段映射。
- 微博、小红书、知乎、贴吧、抖音需登录态、验证码或请求签名，**未做绕过**，因此暂不接入；如需覆盖，应走平台商业接口或授权数据服务。
- 关键词聚合为启发式，可能漏合并（不同措辞差异过大）或误合并（已用模板剥离收敛）；阈值可在 `keywords.ts` 调整。启用大模型整合可显著改善归一效果。
- 采集频率克制（默认每小时），只抓公开列表，不做深度爬取；摘要入库前脱敏。
