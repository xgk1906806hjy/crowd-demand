## 1. 功能目标

把「一句话需求」转化为「可执行、可报价、可验收的方案」。需求达标进入竞标后，开发者提交需求理解、技术规格、报价与工期，由发起者横向比较选择，避免照着模糊需求直接开发。

## 2. 用户故事

- 作为已认证开发者，我想对竞标中的需求提交方案与报价，以便争取项目。
- 作为发起者，我想看到多份方案的理解、规格、报价、工期和开发者信誉，以便做出选择。
- 边界场景：
  1. 未申请开发者角色 → 提示先申请。
  2. 同一需求重复提交 → 冲突提示，不产生第二份。
  3. 报价超过托管总额 → 拒绝（否则中标后无法兑付）。

## 3. 详细需求

### 3.1 输入

| 字段 | 类型 | 必填 | 校验规则 |
| --- | --- | --- | --- |
| needId | path | 是 | 状态必须为 BIDDING |
| understanding | string | 是 | 30-2000 字 |
| spec | string | 是 | 50-10000 字 |
| quoteYuan | string/number | 是 | >0，且 ≤ 需求已托管金额 |
| durationDays | number | 是 | 1-365 整数 |
| pastCases | string | 否 | ≤2000 字 |

### 3.2 输出

`{ id, status: SUBMITTED }`；列表返回开发者昵称、信誉分、报价、工期、方案全文。

### 3.3 业务规则

1. **角色 + 实名双门槛**：必须拥有 `BUILDER` 角色且 `kycStatus = VERIFIED`。
2. **竞标期限制**：仅 `BIDDING` 可提交；`PLEDGING` 及之前不可见/不可投。
3. **一需求一提案**：`@@unique([needId, builderId])`。
4. **报价封顶**：`quote ≤ Need.pledgedAmount`，防止超募承诺无法兑付。
5. **列表公开时机**：竞标开始后公开展示，之前返回空列表。
6. **审计**：提交写 `AuditLog`（PROPOSAL）。

### 3.4 状态流转

```
提案：SUBMITTED（待选） → SELECTED（中标）/ REJECTED（未中选）
```

### 3.5 权限

| 角色 | 可执行操作 |
| --- | --- |
| 未登录 | 可浏览竞标中的提案 |
| 已登录普通用户 | 浏览提案 |
| 已实名 + 开发者 | 提交提案、查看我的提案 |
| 需求发起者 | 浏览提案、选标（F13） |
| 运营方 | 浏览全部提案 |

- 涉及模块：`src/domain/proposal/service.ts`、`src/app/api/needs/[id]/proposals/route.ts`、`src/components/need/proposal-form.tsx`、`src/app/(console)/console/proposals/page.tsx`

- 资金：不涉及资金操作（报价只是要约，实际放款在 F16）

## 5. 验收标准

- [x] 核心流程可用：开发者提交方案，发起者可见
- [x] 异常场景有明确提示：角色、实名、状态、长度、报价上限、重复提交
- [x] 单元测试通过：`tests/unit/proposal-service.test.ts`（提交 7 例）
- [x] 报价不超过托管金额
- [ ] 提案附件与作品集（F24，M3）

## 6. 测试要点

1. 非开发者 / 未实名 / 非竞标期三类拒绝。
2. 理解与规格长度边界。
3. 报价 = 托管额（通过）、托管额 +1 分（拒绝）。
4. 重复提交返回 CONFLICT。
5. 提交成功状态 SUBMITTED。
