## 1. 功能目标

用唯一的状态机管理需求从草稿到完成/退款的完整生命周期，杜绝 UI 或接口层各自判断状态导致的数据不一致，并让每一次流转都可追溯（谁、何时、从什么状态到什么状态、为什么）。

## 2. 用户故事

- 作为发起者，我想把草稿发布出去，或在没人投票时撤销需求。
- 作为运营方，我想按业务进程推进需求状态（达标进入竞标、开始开发、进入验收）。
- 边界场景：
  1. 发起者想把 COLLECTING 直接改成 COMPLETED → 拒绝（越权且跳级）。
  2. 并发两次「票数达标」都尝试转 PLEDGING → 条件更新只成功一次。
  3. 已完成的需求再被流转 → INVALID_STATE。

## 3. 详细需求

### 3.1 输入

| 字段 | 类型 | 必填 | 校验规则 |
| --- | --- | --- | --- |
| needId | path | 是 | 必须存在 |
| to | NeedStatus | 是 | 必须是合法枚举值且满足状态机 |
| reason | string | 否 | 流转原因，写入状态日志 |

### 3.2 输出

`{ id, status }`，同时新增一条 `NeedStatusLog` 与一条 `AuditLog`。

### 3.3 业务规则

1. **唯一真相来源**：`NEED_TRANSITIONS` 定义全部合法流转，任何层不得绕过。
2. **发起者权限收窄**：仅允许 `DRAFT→COLLECTING`（发布）与 `COLLECTING→FAILED`（撤销）。
3. **运营方权限**：可执行任意**合法**流转，非法流转仍被拒绝。
4. **必须有日志**：业务更新与状态日志在同一事务提交。
5. **首次发布补 publishedAt**：`DRAFT→COLLECTING` 时若 `publishedAt` 为空则写入当前时间。
6. **终态封闭**：`COMPLETED`、`REFUNDED` 无出边。
7. **流拍即退款**：流转到 `FAILED` 时自动调用全额退款，退款完成后同链路流转到 `REFUNDED`；开发中/验收中的需求不允许直接流拍（涉及已放款项目，必须走结算）。
8. **事务内唯一入口**：所有领域服务改需求状态必须调用 `transitionNeedInTx()`（条件更新 + 状态机校验 + 日志），禁止散落的 `need.update({ status })`。

### 3.4 状态流转

```
DRAFT ──发布──→ COLLECTING ──票数达标──→ PLEDGING ──承诺达标──→ BIDDING
                    │                        │                    │
                    └────撤销/到期未达标──────┴────────────────────┴──→ FAILED ──退款──→ REFUNDED

BIDDING ──中标──→ IN_PROGRESS ──提交里程碑──→ ACCEPTING ──验收完成──→ COMPLETED
                                                              └──验收不通过──→ REFUNDED
```

### 3.5 权限

| 角色 | 可执行操作 |
| --- | --- |
| 需求发起者 | 发布草稿、撤销征集中的需求 |
| 支持者 | 无 |
| 开发者 | 无（后续由中标流程触发） |
| 运营方 | 任意合法流转（含强制流拍） |

## 4. 技术实现

- 涉及模块：`src/domain/need/state-machine.ts`、`src/domain/need/transition.ts`（事务内唯一流转入口）、`src/domain/need/service.ts`（`transition`）、`src/domain/pledge/lifecycle.ts`（`failNeedAndRefund`）、`src/app/api/needs/[id]/status/route.ts`、`src/components/need/need-actions.tsx`
- 数据库变更：无（使用 `Need.status` 与 `NeedStatusLog`）
- 事务：`need.update` + `needStatusLog.create` 在同一 `$transaction`
- 并发控制：全部自动流转使用 `updateMany({ where: { id, status: from } })` 条件更新，只有一方成功
- 外部依赖：无

## 5. 验收标准

- [x] 核心流程可用：发布、撤销、运营推进
- [x] 异常场景有明确提示：非法流转返回「不允许从 A 流转到 B」
- [x] 单元测试通过：`tests/unit/need-state-machine.test.ts`（7 例）+ `need-service.test.ts`（状态流转 6 例）
- [x] 每次流转写 `NeedStatusLog` 与审计日志
- [x] 流转到 `FAILED` 自动退款并收口到 `REFUNDED`（未退完保持 `FAILED`，可重入重试）
- [x] 定时任务自动流拍（内部 cron 接口 + 部署侧 cron 容器）

## 6. 测试要点

1. 全部合法流转逐条验证；代表性非法流转（跳级、回退、终态出走）全部拒绝。
2. 发起者越权流转被拒绝且状态不变。
3. 运营方合法流转成功，非法流转仍失败。
4. 流转日志 `fromStatus` / `toStatus` / `reason` 正确。
5. 并发达标只产生一条 PLEDGING 日志（F07 测试覆盖）。
