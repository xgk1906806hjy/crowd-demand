## 1. 选型依据

本项目四个硬性约束决定了技术栈：

1. **资金正确性**：涉及订金、托管、放款、退款，需要强事务、行锁、整数分记账 → 选 PostgreSQL + 事务账本，不用 NoSQL 做主存储。
2. **多角色 + 状态机**：需求/承诺/提案/里程碑都有严格状态流转 → 需要类型系统强、可建领域层的语言 → TypeScript。
3. **快速验证 MVP**：团队小、要先跑通闭环 → 全栈一套语言、一个仓库，减少联调成本。
4. **发现属性**：需求广场需要被搜索引擎收录 → 首屏 SSR/SSG 友好。

## 4. 关键设计决策

### 4.1 为什么用 Next.js 全栈而不是前后端分离

- MVP 阶段只有一个团队，全栈一套语言最快；Route Handlers 做 BFF 足够。
- 领域层（`src/domain`）独立成 service，未来若需拆成独立后端，可直接迁移，前端改动小。
- SSR 满足需求广场的 SEO 需求。

### 4.2 支付/托管适配器

```ts
interface PaymentGateway {
  freeze(params): Promise<FreezeResult>   // 承诺：冻结到托管
  release(params): Promise<ReleaseResult> // 放款：托管→开发者
  refund(params): Promise<RefundResult>   // 退款：托管→支持者
  query(params): Promise<PaymentStatus>
}
```

- `MockPaymentGateway`：本地/测试环境，账本模拟，用于跑通流程与测试。
- 生产实现：按合规要求接入持牌第三方（如银行存管 / 持牌支付机构的分账能力），业务代码零改动。
- **红线**：不自建资金池，不用个人账户周转。

### 4.3 数据库事务与账本

- 金额字段统一 `BigInt`（单位：分），展示层再格式化为元。
- 每笔资金操作：开启事务 → 取 `pg_advisory_xact_lock` 串行化 → 读余额 → 写 ledger 流水 → 更新业务状态 → 提交；任一步失败整体回滚。
- 托管账户出账前校验余额 ≥ 金额，余额不足直接抛错，防并发超额放款。
- 幂等键唯一索引，重复请求不会重复记账/重复退款。

## 6. 备选方案（若团队技术栈不同）

| 场景 | 替代方案 |
| --- | --- |
| 团队更熟 Vue | Nuxt 3 + Prisma + PostgreSQL（架构对齐，SEO 同样友好） |
| 领域复杂度高、要长期演进 | 拆分 NestJS 后端 + Next.js 前端，领域层平滑迁移 |
| 无运维能力 | 数据库用 Supabase（PostgreSQL），部署用 Vercel + 云 OSS |

> 无论选哪种替代，**资金用整数分 + 事务账本 + 幂等键**、**状态机集中管理**、**支付走适配器**这三条不可妥协。
