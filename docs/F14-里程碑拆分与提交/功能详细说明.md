## 1. 功能目标

把一次性放款拆成可验收的节点，降低「钱付了但东西没做出来」的风险。中标开发者在开工前定义节点、交付物与放款比例；每完成一个节点提交交付物，等待发起者验收。

## 2. 用户故事

- 作为中标开发者，我想把项目拆成 2-5 个节点并约定放款比例，以便按阶段拿到钱。
- 作为发起者，我想看到清晰的交付物与验收标准，以便逐节点验收。
- 边界场景：
  1. 比例合计 99% → 拒绝并提示当前合计。
  2. 重复拆分 → 冲突，不允许覆盖已定节点。
  3. 非中标开发者尝试拆分 → 拒绝。

## 3. 详细需求

### 3.1 输入

| 字段 | 类型 | 必填 | 校验规则 |
| --- | --- | --- | --- |
| projectId | path | 是 | 项目存在且状态 IN_PROGRESS |
| items[].title | string | 是 | 2-60 字 |
| items[].deliverable | string | 是 | 10-2000 字 |
| items[].releaseRatio | number | 是 | 万分比，>0，合计必须 10000 |
| items 数量 | number | 是 | 1-5 个 |
| note | string | 否 | 提交交付物时的说明，≤2000 字 |

### 3.2 输出

- 拆分：`{ count }`，生成 `Milestone` 记录（seq、releaseRatio、releaseAmount）。
- 提交：`{ status: SUBMITTED }`，需求转 `ACCEPTING`。

### 3.3 业务规则

1. **金额基数 = 中标报价**（不是托管总额），差额在 F17 结算时按比例退回。
2. **取整策略**：按比例向下取整，最后一个节点承接余数，合计精确等于报价。
3. **一次性拆分**：项目已有节点时拒绝再次拆分。
4. **提交权限**：仅中标开发者或运营方。
5. **状态联动**：首次提交节点时需求 `IN_PROGRESS → ACCEPTING`，写状态日志。
6. **审计**：拆分与提交均写 `AuditLog`（MILESTONE）。

### 3.4 状态流转

```
节点：PENDING ──提交交付物──→ SUBMITTED
需求：IN_PROGRESS ──首次提交节点──→ ACCEPTING
```

### 3.5 权限

| 角色 | 可执行操作 |
| --- | --- |
| 中标开发者 | 拆分里程碑、提交节点 |
| 需求发起者 | 查看进度 |
| 其他用户 | 只读 |
| 运营方 | 可代为拆分与提交 |

- 资金：本功能不动钱，只定义比例

## 6. 测试要点

1. 非中标开发者拆分/提交均拒绝。
2. 比例合计 60%、300% 等非法值拒绝。
3. 拆分后金额合计 = 报价；50/50 时各 40000（报价 80000）。
4. 重复拆分返回 CONFLICT。
5. 提交后节点 SUBMITTED、需求 ACCEPTING、日志 1 条。
