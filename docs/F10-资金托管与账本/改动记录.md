## 详细记录

### v0.1 — 2026-11-21 — 新建

- 背景：技术栈与开发方案要求「不存余额、只记流水」，用复式账本保证资金可对账、可追溯。
- 改动内容：
  - 新增 `src/domain/ledger/service.ts`：
    - `postTransfer(tx, input)`：一借一贷写两条 `LedgerEntry`，含 `balanceAfter` 快照。
    - `balanceOf(db, account)`：`ΣCREDIT − ΣDEBIT` 推导余额。
    - 账户工厂 `backerAccount` / `builderAccount` / `ESCROW_ACCOUNT`。
    - 幂等键派生 `:out` / `:in`，依赖数据库唯一约束防重复记账。
  - 金额全程 `bigint`（分），零/负金额直接抛错。
- 影响范围：
  - F09 承诺、F11 退款、后续 F16 放款、F17 结算全部复用此模块。
  - 任何业务不得直接改余额字段（项目内不存在余额字段）。
- 验证方式：
  - `npm run typecheck`：0 错误
  - `npm test`：89 用例全绿（账本 6 例：借贷守恒、余额快照、冲销归零、幂等键）
  - `npm run build`：EXIT=0，26 条路由全部生成（含 6 个新 API 与 1 个新页面）

### v0.2 — 2026-11-23 — Bug 修复

- 背景：`postTransfer` 直接读全量流水算余额，无行锁，并发事务会互相覆盖 `balanceAfter`；且从托管出账不校验余额，可能负余额。
- 改动内容：
  - 新增 `lockLedger(tx)`：`SELECT pg_advisory_xact_lock(hashtext('crowd-demand:ledger'))`，事务结束自动释放；所有记账在锁内完成。
  - `postTransfer` 增加护栏：出账方为 `ESCROW` 且余额 < 金额时抛「托管账户余额不足」。
  - `LedgerTx` 类型扩展为 `ledgerEntry + $queryRaw`；测试内存库补 `$queryRaw` 空实现。
- 影响范围：F09 承诺、F11 退款、F16 放款、F17 结算全部经由该护栏。
- 验证方式：`tests/unit/ledger.test.ts` 增至 8 例（余额不足拒绝、余额恰好放款归零）；`npx vitest run` 125 例全绿。

### v0.3 — 2026-11-23 — 生产环境 Bug 修复

- 背景：真实部署后**所有**涉及记账的接口（付费承诺、退款、放款）返回 500。日志报 `PrismaClientKnownRequestError P2010`：`Failed to deserialize column of type 'void'`。原因是 `SELECT pg_advisory_xact_lock(...)` 返回 `void` 类型，Prisma `$queryRaw` 无法反序列化该列。单元测试用的是内存 mock，从未真正执行过该 SQL，因此一直未暴露。
- 改动内容：
  - `lockLedger()` 改为 `SELECT 1::int AS locked FROM (SELECT pg_advisory_xact_lock(hashtext('crowd-demand:ledger'))) AS _lock`：把 `void` 列包进子查询并投影出 `int` 列，保留加锁副作用，规避反序列化失败。
- 影响范围：F09 承诺、F11 退款、F16 放款、F17 结算全部恢复可用；锁语义不变（事务级、提交/回滚自动释放）。
- 验证方式：
  - 部署环境端到端冒烟：承诺 600 + 400 成功、幂等重放返回同一 pledgeId、达标自动进入竞标、验收触发放款全部通过。
  - 教训：涉及数据库原生 SQL 的路径不能只靠 mock 单测，必须有一次真实实例验证。
